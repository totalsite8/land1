От идеи до лендинга на Vercel: повторяемый путь

Это один HTML-файл-инструкция для создания лендинга в любой нише: услуга, физический товар, SaaS, локальный бизнес, B2B или личный бренд. Он не зависит от конкретного названия, продукта или клиента. На каждом этапе Agent Mode дополняет этот файл: фиксирует действие, решение, проверку и следующий шаг.

Статус шаблона: техническая база ставится сразу; дальше работа идёт от исследования аудитории к стратегии, контенту, разработке, запуску и улучшениям. Не перескакивайте через исследование ради «быстрого дизайна».

0. Правила результата

  1. Нельзя гарантировать 100% конверсию: на неё влияют трафик, цена, спрос, доверие и сам продукт. Цель — убрать максимум барьеров и повышать конверсию по данным.
  2. Не выдумывайте отзывы, клиентов, сертификаты, цены, интеграции, результаты, дефицит или сроки.
  3. Не продавайте «всем». Первая версия всегда адресована одному приоритетному сегменту и одному главному действию.
  4. Hero-блок должен быть следствием продукта и боли аудитории. WebGL — только если объясняет идею, а не ради декоративного эффекта.
  5. Сначала понятная HTML/CSS-версия, затем motion и WebGL как progressive enhancement. Контент и CTA должны работать без них.

1. Доступы и рабочая среда

  1. Если сервисы недоступны в вашей стране, включите подходящий законный VPN. Не передавайте пароль, 2FA-коды, токены или ключи в чат.
  2. Создайте аккаунт на GitHub, подтвердите e-mail и включите двухфакторную защиту.
  3. На GitHub: + → New repository → понятное имя → Private при наличии материалов клиента → Add README → Create repository.
  4. Откройте Arena.ai, войдите через Google, создайте чат в Agent Mode и подключите GitHub-репозиторий.
Мы создаём лендинг от исследования до запуска. Веди проект небольшими этапами и после каждого обновляй landing-journey.html: что сделали, зачем, принятые решения, проверка, следующий шаг и готовый промпт. Не придумывай факты и не используй AI-шаблоны. Работай в подключённой ветке репозитория.

2. Установите технический фундамент сразу

Этот стек безопасно работает на бесплатном Vercel и оставляет возможность сделать нестандартный hero-блок.

  • Next.js + React + TypeScript — сайт, SEO, сборка и деплой.
  • Three.js + React Three Fiber + Drei — WebGL, если он нужен концепции.
  • GSAP — осмысленная анимация.
  • Lucide, clsx, ESLint, Prettier — интерфейс и качество кода.
  • robots.txt, .htaccess, vercel.json, sitemap — техническая и SEO-база. Vercel применяет vercel.json; .htaccess оставляют для Apache-совместимого хостинга.
Подготовь в репозитории Next.js-проект с TypeScript. Установи three, @react-three/fiber, @react-three/drei, gsap, lucide-react, clsx, ESLint и Prettier. Создай базовые robots.txt, .htaccess, vercel.json, sitemap и .gitignore. Настрой проект для бесплатного Vercel. Запусти npm run lint и npm run build. Обнови landing-journey.html с перечнем файлов и результатами проверки.

3. Выберите нишу, сегмент и главное действие

Ниша — это связка кто → в какой ситуации → какую проблему решает → к какому действию ведём. Не «маркетинг», а «собственник небольшой сети точек, который не видит, что передали между сменами».

Помоги сузить нишу для лендинга. Пока не делай дизайн и код.
Продукт/идея: [вставьте]
Предполагаемая аудитория: [вставьте]
География и язык: [вставьте]
Проблема: [вставьте]
Главное действие: [заявка / покупка / бронь / предзаказ]
Материалы: [фото, кейсы, брендбук, ничего]
Задай до 8 вопросов. После ответов предложи до 3 узких сегментов. Для каждого укажи контекст, боль, ценность, риск и причину выбрать/не выбрать его для первого запуска. Не выдумывай исследования.

Результат: один первичный сегмент, одна проблема и одно измеримое действие.

4. Проведите глубокое интервью до дизайна

Даже если нет доступа к клиентам, отделите известные факты от гипотез. Не пишите «качественно», «быстро», «удобно» без примера. Для каждого ответа спрашивайте: «в какой ситуации?», «что происходит потом?», «как это говорит сам клиент?», «чем уже пытался решить?».

Работай как продуктовый исследователь, копирайтер и арт-директор. Проведи интервью раундами не более 8 вопросов за раз. Исследуй: состав продукта и ограничения; кто платит, решает и пользуется; момент возникновения проблемы; дословный язык клиента; стоимость бездействия; альтернативы; возражения; реальные доказательства; юридические ограничения; визуальные анти-референсы. После интервью выдай заполненный бриф, факты отдельно от гипотез, карту «контекст → боль → результат → барьер → доказательство → CTA» и список отсутствующих данных. Не пиши код.

5. Утвердите оффер и сценарий конверсии

Оффер отвечает на три вопроса за первые секунды: «это для меня?», «что изменится?» и «почему верить?». Страница — последовательность снятия сомнений, а не набор модных блоков.

На основе брифа предложи 3 варианта позиционирования. Для каждого: заголовок hero, подзаголовок, конкретный результат, ограничение обещания, CTA и необходимое доказательство. Затем выбери один вариант с объяснением. Построй архитектуру страницы: для каждого блока назови вопрос посетителя, цель, тезис, доказательство, формат и CTA. Отдельно опиши мобильный сценарий. Не используй типовой набор секций без связи с исследованием.

Результат: утверждённый оффер, структура страницы, поля формы и критерии целевой заявки.

6. Создайте визуальную концепцию и hero

Ищите метафору в реальном продукте: материале, процессе, маршруте, трансформации, данных, среде или физическом действии. Не берите абстрактные сферы, частицы, градиенты и «неон» только потому, что это выглядит как AI.

Предложи 3 визуальные концепции для утверждённой стратегии. Для каждой укажи: метафору и её связь с болью; что видно в первую секунду; заголовок и CTA; интеракцию; технологию (CSS, SVG, видео или WebGL); список реальных материалов; fallback для мобильных и prefers-reduced-motion; риск непонимания. Не используй декоративный 3D без смысла. Порекомендуй одну концепцию и жди подтверждения.

7. Подготовьте контент и доказательства

Соберите реальные фотографии, интерфейсы, документы, процесс, кейсы и отзывы с разрешением. Если доказательств нет, честно используйте статус «ранний доступ», «пилот» или «в разработке», а не создавайте фиктивную репутацию.

Напиши контент для утверждённой структуры. Для каждого блока дай заголовок, текст, доказательство, CTA и микрокопию. Любой отсутствующий факт пометь [НУЖНО ПОДТВЕРДИТЬ]. Создай список изображений/видео: что должно быть на кадре и зачем. Проверь текст на штампы, ложные обещания, юридические риски, язык аудитории и чтение с телефона. Не пиши код.

8. Реализуйте лендинг

  1. Сначала семантика, сетка, типографика, форма и responsive-версия.
  2. Если на странице есть каталог (продукты, услуги, тарифы), каждой позиции нужен отдельный якорный блок с уникальным id: подробное описание, кому подходит и CTA. Список каталога работает оглавлением со ссылками на эти блоки, а не набором одинаковых ссылок на форму.
  3. Якорные блоки каталога держите на единой рамке, но не клонируйте содержимое: у каждой позиции свой узнаваемый сценарий. Рабочий каркас блока — узнаваемая рабочая ситуация, одна конкретная боль, честный статус («пилот», «проверяем спрос», «в разработке»), что именно проверяется, три шага сценария и CTA. Дополняйте каждый блок собственной смысловой схемой «вход → действие → видимый результат» (inline-SVG, не декоративная абстракция), чтобы структуру можно было понять и без чтения текста.
  4. Контент каталога храните в одном источнике данных (отдельный файл с массивом записей), а разметку секций генерируйте из него: тогда добавление позиции — это одна запись, а не правка вёрстки. После любого расширения проверяйте скриптом, что каждая ссылка-якорь в оглавлении ведёт на существующий id и ни один id не дублируется.
  5. Затем интеракции и анимации.
  6. В последнюю очередь — лениво загружаемый WebGL. Дайте статичный CSS/SVG fallback.
  7. Форма должна иметь загрузку, настоящий успех, ошибку и понятный следующий шаг. Никогда не показывайте «заявка отправлена», пока сервер не подтвердил отправку. Секреты обработчика хранятся только в Vercel Environment Variables.
Расширь каталог лендинга новыми позициями. Для каждой: номер, название, честный статус, одна узнаваемая рабочая ситуация, одна боль без штампов, что проверяем в пилоте/первой версии, три шага сценария и CTA в форму. Контент добавляй в единый источник данных каталога, а не в разметку. Каждой позиции нарисуй уникальную inline-SVG схему «вход → действие → видимый результат» с подписями зон и aria-label. Ссылки оглавления привяжи к id якорных блоков. Проверь мобильную вёрстку, совпадение якорей и id, затем запусти npm run lint и npm run build.
Реализуй утверждённый лендинг в текущем Next.js-проекте. Работай mobile-first. Используй семантический HTML, контраст, клавиатурную навигацию, focus-состояния, alt-тексты и prefers-reduced-motion. Hero сначала сделай доступным HTML/CSS/SVG; WebGL добавь динамически и только как улучшение. Не добавляй неутверждённые факты. Перед завершением запусти npm run lint и npm run build, исправь ошибки. Обнови landing-journey.html: файлы, результаты проверок и незакрытые production-задачи.

Если LIVE PREVIEW показывает runtime-ошибку Next.js

После крупных изменений в client-компонентах или WebGL dev-сервер иногда держит несовместимый HMR/React Client Manifest кэш. Не пытайтесь лечить это правками интерфейса. Остановите dev-сервер, удалите .next, выполните npm run build и откройте production-предпросмотр командой npm run start -- --hostname 0.0.0.0. Проверка считается успешной только при HTTP 200 на / и успешной production-сборке.

9. Проверьте конверсию, доступность и скорость

  • За 5–10 секунд понятно: кому это, что меняется и что нажать.
  • CTA виден на телефоне; форма заполняется без лишних полей.
  • Проверены табуляция, контраст, reduced motion, отсутствие горизонтальной прокрутки и ошибки консоли.
  • Лендинг не зависит от WebGL, внешнего шрифта или тяжёлого видео для понимания основного смысла.
  • Все отзывы, цифры и условия можно подтвердить.
Проведи аудит лендинга как холодный представитель целевой аудитории, UX-редактор, accessibility-специалист и performance-инженер. Назови до 5 приоритетных проблем: где они находятся, почему снижают конверсию, как исправить, ожидаемый эффект и риск. Не меняй всё сразу — жди выбора. После выбранных правок снова запусти lint и build и обнови инструкцию.

10. Опубликуйте на Vercel

  1. Войдите на Vercel через GitHub.
  2. Add New → Project → импортируйте репозиторий.
  3. Проверьте, что выбран Next.js, Build Command — npm run build, затем нажмите Deploy.
  4. Подключите домен: Settings → Domains. Внесите DNS-записи, которые покажет Vercel.
  5. Только после домена обновите metadata, robots.txt и sitemap на фактический URL.
  6. Добавьте секреты формы в Settings → Environment Variables, а не в Git или чат.
Подготовь текущий проект к production на Vercel для домена [домен]. Проверь metadata, favicon, Open Graph, sitemap, robots.txt, форму, заголовки безопасности и переменные окружения. Составь отдельный ручной чек-лист действий в Vercel и DNS. Не записывай секреты в репозиторий. Выполни lint и build, затем обнови landing-journey.html.

Где посмотреть сайт и где добавить переменные Vercel

  1. Во время разработки в Arena: откройте LIVE PREVIEW, который появляется у запущенного сервера, прямо из интерфейса Arena. Это временный просмотр, не публичный production-сайт. Не пересылайте его URL как публичную ссылку: sandbox может требовать внутренний traffic access token, который Arena добавляет только при открытии preview-карточки.
  2. Получить бесплатный адрес Vercel: откройте Vercel Dashboard → Add New… → Project → рядом с нужным GitHub-репозиторием нажмите Import → оставьте Framework Preset Next.js → Deploy. После первого деплоя Vercel покажет адрес вида project-name.vercel.app.
  3. Почему не видно Environment Variables: они находятся внутри уже импортированного проекта, а не в общем списке Vercel. Откройте Dashboard → выберите карточку проекта → Settings → в левом меню Environment Variables. В некоторых версиях интерфейса раздел может называться Environment Variables в верхней вкладке Settings.
  4. Что добавить: TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID и после первого деплоя NEXT_PUBLIC_SITE_URL со значением выданного адреса https://…vercel.app. Выберите окружения Production, Preview и Development, затем сделайте Redeploy. Никогда не вставляйте токены в Git, исходный код или чат.
  5. Свой домен позднее: Settings → Domains → Add Domain → укажите домен. В панели регистратора внесите DNS-записи, которые покажет Vercel. Затем замените значение NEXT_PUBLIC_SITE_URL на новый URL и сделайте Redeploy. Не нужно покупать домен для первого теста.

Пока переменная NEXT_PUBLIC_SITE_URL не задана, сайт намеренно закрыт от индексации: robots и sitemap не публикуют тестовый адрес. Это предотвращает случайную индексацию preview-версии.

11. Улучшайте по данным, а не по вкусу

Выберите одно главное событие: покупка, заявка, бронь или предзаказ. Дополнительно фиксируйте просмотры CTA, начало формы, ошибки формы и отправку. Собирайте обратную связь, формулируйте одну гипотезу, меняйте одну причину и сравнивайте результат.

Вот данные после запуска: [метрики, записи разговоров, сообщения, проблемы]. Отдели факты от интерпретаций. Предложи максимум 3 гипотезы роста: проблема, сегмент, изменение, метрика успеха, необходимый объём данных, риск. Ничего не реализуй до выбора. После реализации зафиксируй в landing-journey.html, что изменилось и какой результат получен.
Главное правило: после каждого шага обновляйте этот файл. Так любой следующий проект начинается не с пустого чата, а с понятного, проверяемого процесса.
